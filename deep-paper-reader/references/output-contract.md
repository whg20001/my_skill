# Output Contract：各模式的输出结构与格式

> 输出前读取。`full` 笔记文件以 `assets/reading-note-template.md` 为骨架；其余模式不套整篇模板。讲解技法见 `teaching-playbook.md`。

## 1. 共同规则

- **语言**：中文；模型、数据集、指标等专名保留原词，首次出现给中英对照（适用时）。
- **公式**：行内 `$x$`，块级 `$$...$$`；变量名、上下标与编号与原文一致。若为教学重新编号，要说明。
- **锚点**：核心技术断言附 `（§3.2, Eq.(4)）`、`（Fig.2）`、`（Table 3）`。页码只在核实后写；无法确认写 `原文定位未核实`。
- **论断性质**：重要内容用 `[原文事实]`、`[解释性分析]`、`[背景知识]`、`[推测/待验证]`。“原文事实”指论文确实这样写/报告，不代表已被独立证明。
- **缺失信息**：`原文未报告`（找过该部分仍没有）与 `当前材料未覆盖`（没读到）不可混用。
- **覆盖状态**：总是写明来源、版本与 `complete` / `partial` / `abstract-only`。`complete` 只表示指定正文已读，不代表附录、补充材料、参考文献都逐条核实。
- **自拟内容**：Toy Example、教学伪代码、补充推导都标“自拟”或“教学整理版”；不要把想象的实验、实现或超参数写成论文事实。
- **紧凑**：优先方法链与证据，不复述引言、不整表照抄；适当用简表。不为“完整”而写空段落。

### 1.1 首次分析后的固定选择（所有模式共用）

- **触发时机**：在当前对话中，首次完成对某篇论文的实质分析并交付结果后，作为聊天回复的最后一部分追加下方菜单。适用于 `quick`、`focused`、`interactive` 和 `full`；不把菜单写入十节笔记正文，不在分析前用菜单阻断用户请求。
- **首次判定**：依据当前对话中可见的论文身份与已交付分析判断，不创建跨对话的用户追踪记录。同一论文后续追问、继续带读、补充材料或版本更新不重新触发；换一篇论文则重新触发。仅确认收到文件、汇报进度或读取失败不算完成分析；若基于摘要/部分材料已做实质分析，照样给菜单，但必须保留 `abstract-only` / `partial` 覆盖说明。
- **固定菜单**：保留编号、名称和顺序；说明可以简短，但不能合并或增加第四个选项：

```markdown
接下来你可以选择：
1. **逐步带读**：每次讲一个逻辑单元，边读边理解。
2. **完整精读**：系统梳理全文，整理完整精读笔记。
3. **其他要求**：直接告诉我你想重点了解什么。

回复 1、2、3，或直接描述你的要求即可。
```

- **处理选择**：`1` → `interactive`，沿已读进度或用户指定起点带读；`2` → `full`，生成或完善十节精读笔记；`3` → 若未附具体要求，简短询问想了解什么，若已附要求则直接处理。用户也可直接提问，不必先回复数字；有歧义时先澄清，不把公式编号等误当菜单选择。
- **避免重做**：如果首次交付已经是完整精读，菜单第 2 项仍保留“完整精读”名称，可说明“已完成，可继续补充或深化”；用户选择后基于已有笔记继续，不无故从头重复。选择完整精读不会解除来源不足的限制：缺正文时先索取所需材料，不能把摘要补成全文。
- **与其他结尾规则的关系**：本菜单取代首次交付中旧的“是否进入 full 或 interactive”问句；首次 `interactive` 回复不再另加一组 A/B/C 路线，可保留一个理解检查题。后续带读按原有节奏给本轮的局部下一步选项，不反复展示首次菜单。用户明确要求不提供菜单、不要追问或严格限制输出格式时，以用户要求为准。

## 2. QUICK 速览

用于“这篇讲了什么 / 值不值得读”。一屏左右，不展开推导：

```markdown
**来源与覆盖**：标题、版本、complete/partial/abstract-only

**一句话**：研究问题 + 核心想法（不夸大）
**它解决的卡点**：现有方法在什么情况下不行（锚点）
**核心想法**：2–4 句讲机制，不堆术语
**关键证据**：1–3 条最重要的结果（指标、数值、对照、表号）
**读之前需要知道**：2–4 个前置概念，各一句 [背景知识]
**建议精读顺序**：例如 §3.2 → Eq.(5)–(7) → Table 3 → §5，并说明理由
**先保留的疑问**：1–2 个读速览时就能看出的证据缺口
```

该论文首次分析的结尾按 §1.1 给出“逐步带读 / 完整精读 / 其他要求”三个选择，不再使用原来的二选一问句；同篇后续速览不重复首次菜单。

## 3. FULL 精读

固定 10 个二级标题，顺序如下（`scripts/lint_report.py` 依赖这些标题）。论文不涉及某项时写一句“本文不涉及”，不要伪造内容：

```markdown
# [论文标题]｜深度精读笔记

## 0. 论文来源与覆盖
## 1. 核心观点与阅读导航
## 2. 研究问题与动机
## 3. 核心贡献与整体方法
## 4. 模块、算法与关键公式
## 5. 实验设计与证据分析
## 6. 局限性与批判性思考
## 7. 直观例子与理解检验
## 8. 论断—原文证据索引
## 9. 技术洞察与开放问题
```

### §0 来源与覆盖
标题、来源类型/链接、可核实版本、覆盖状态、是否读了附录、无法核实的内容。版本未知写“版本未核实”。只有摘要时不得出现“全文已精读”。

### §1 核心观点与阅读导航
- **一句话理解**（事实与解释分开）。
- 2–4 项作者贡献，按重要性排序；内容有限可少于 2 项。
- **阅读主线**：卡点 → 问题定义 → 方法 → 证据。
- **前置知识**：2–5 个必需概念，每个 1–3 句，标 `[背景知识]`。
- **术语表**（可选，术语多时）：原词 / 中文 / 本文中的含义 / 首次出现位置。

### §2 研究问题与动机
任务定义（输入、输出、目标函数或约束）、现有方法的瓶颈、作者明确提出的动机。必要时数学形式化，不自造论文术语。区分“作者认为现有方法有问题”与“现有方法客观上都有该问题”。

### §3 核心贡献与整体方法
- 逐项区分新内容与复用组件。
- 一条完整数据流；训练与推理不同时分开写。
- 先给全景，让读者在进入 §4 前知道每个模块的位置。
- 知识点与架构图优先采用增强型 Markdown（HTML / iframe / 受支持的脚本或组件扩展）配合交互式 SVG，并提供静态 SVG 与交互版链接回退。遵循 `interactive-svg.md`，按实际查看器验证资源路径与关键交互，不假设所有 MD 查看器都支持脚本。

### §4 模块、算法与关键公式
- 展开最重要的 1–4 个单元，每个按“卡点 → 直觉 → 原式/符号/形状 → 例子 → 回到原文 → 边界”组织（见 `teaching-playbook.md` §1）。
- 重要公式适合逐步计算时，优先就地加入小型动态 SVG，展示输入、运算、中间量和最终输出，并保留可静态阅读的计算过程；与正文数值和符号一致。交互图风格参照已查看的论文框架图，教学重绘及缩小维度要明确标注（见 `interactive-svg.md`）。
- 架构图要沿数据流讲一遍（见 `teaching-playbook.md` §6）。
- 补充推导与 Toy Example 与原文陈述分开。方法简单、没有公式时聚焦算法与实现逻辑，不人为加公式。
- **复现要点**（小表）：数据处理、模型配置、训练设置、评估协议，各标 `原文已给出（锚点）` / `原文未报告`。

### §5 实验设计与证据分析
- 数据、指标及方向、基线、对照设置。
- 主实验、消融、资源开销（论文涉及且可读时）。
- 每个核心命题的证据强度：直接支持 / 有限支持 / 不支持或无法判断。
- 精确写表号、指标、数值、单位与方向；不虚构误差条或显著性。

### §6 局限性与批判性思考
2–4 项实质审查，标明是论文自述局限还是你的分析；保持“已证实限制 — 未报告 — 推测”的层级。不强制凑固定数量。

### §7 直观例子与理解检验
- 选最关键的一个难点做自拟简化例子，说明简化假设。
- 3–5 道检验机制理解的题（出题法见 `teaching-playbook.md` §8），并在节末附答题要点。

### §8 论断—原文证据索引
至少覆盖问题定义、创新模块、关键公式、主实验、局限（存在时）：

| 关键论断 | 性质 | 原文位置 | 证据状态/限制 |
|---|---|---|---|
| 某模块用于…… | 原文事实 | §3.1 / Fig.1 | 可在原文核实 |
| 某实验显示…… | 原文事实 | Table 2 | 仅支持所测试场景 |
| 某机制可能…… | 推测/待验证 | 无直接实验 | 需要对照验证 |

上表仅为格式示意，不得照抄为实际论文事实。只读到摘要时，位置只能写 `Abstract` 等实际定位。

### §9 技术洞察与开放问题
- 3–5 条机制级洞察（值得带走的“为什么”，不是摘要复述）。
- 可证伪的后续问题或补充实验。
- 尚未读取或未核实的区域及其影响。

## 4. FOCUSED 定向解释

不用 10 节结构。默认包含：

1. **直接回答**：一两句给出最重要的解释。
2. **原文定位**：章节/式/图/表（已核实时）。
3. **必要背景**：理解这个问题必需的定义或上游模块。
4. **逐步解释**：直觉 → 符号/推导/数据流 → 形状与前提核查。
5. **例子**（确实有帮助时）：自拟最小例子。
6. **边界**：哪些是作者的解释、哪些是你的推测；有什么没读到。

小问题不要扩展成全文报告，也不要声称已检查了所有实验。

## 5. INTERACTIVE 带读

节奏细则见 `teaching-playbook.md` §7，固定学习 Map 规则见 §7.1。每轮实质讲解开头展示完整的同一张全局 Map：使用 `text` 代码块和纵向 `↓`，以唯一的 `→` 标记当前模块或分支；主线模块名称、编号与顺序保持不变，comment、quote 等额外追问只增挂对应分支，讲完返回原主线。此导航不使用 Mermaid 或 SVG 替代，机制配图仍可按原规范制作。首轮建立 Map 并建议起点；每轮一个单元。该论文首次实质分析的轮末遵循 §1.1 的固定三个选择，不再重复一组局部路线；后续轮末给可跳过的理解检查和 2–3 个局部下一步选项。追问始终基于同一论文版本与锚点，不混入其他工作。

## 6. Markdown 文件与知识管理

- 文件名 `paper-<arxiv_id_or_slug>-deep-read.md`；没有 arXiv ID 时用中性英文短标题，不在文件名中写不确定的年份。
- 可保留标题、作者、arXiv URL、阅读日期（仅在确知时填写）。不声称已存入外部知识库，不加无效外链或无依据的参考文献列表。
- 无法创建文件时直接返回可复制的 Markdown。
- 配图资源与笔记一起交付；SVG 静态展示与 HTML 交互版共用相同的论文锚点和教学边界说明。静态图不支持交互时仍应能够理解核心方法。

## 7. 格式示例：区分性质

> 仅为格式示例，不对应任何真实论文。

```markdown
**[原文事实]** 作者将门控模块置于特征融合之前（§3, Fig.1）。

**[背景知识]** sigmoid 把任意实数压到 (0,1)，常用来表示“开多大”的软开关。

**[解释性分析]** 因此该结构相当于按样本给两个分支分配权重；
门控接近 1 时主要采用第一分支。

**[推测/待验证]** 在领域迁移时，这可能减少某一分支的噪声影响；
已读实验没有跨域测试，不能认定泛化提升。
```

## 8. 交付前 QA

1. 来源与覆盖范围明确吗？
2. 最重要的贡献、模块与公式确实来自原文吗？
3. 作者声称、实验观察、背景知识与你的推测分开了吗？
4. 核心公式的符号与形状自洽吗？Toy Example 的算术核对过吗？
5. 精确数值都能追溯到表格并匹配指标与方向吗？
6. 有没有把未读附录或看不清的图表说成已核实？
7. 结论是否限定在所报告的数据集、指标与预算内？
8. 最难的概念讲清楚了吗——读者能用自己的话复述吗？
9. 是否符合用户要的模式、深度与语言？

`scripts/lint_report.py` 只检查结构；技术准确性和证据真实性必须对照原文逐项核查。
