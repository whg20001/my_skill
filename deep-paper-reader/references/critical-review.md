# Critical Review：批判性理解与证据边界

> 目的是检验论文结论的范围，促成研究启发，而非为了批判而罗列常见缺陷。

## 1. 区分四种判断

| 类型 | 可使用的表达 | 必要条件 |
|---|---|---|
| 论文明确局限 | `[原文事实] 作者承认……` | 局限章节或对应证据可核实 |
| 实验设计不足 | `[解释性分析] 对于命题 X，实验尚未控制 Y` | 明确命题、实验及缺少的控制 |
| 合理替代解释 | `[推测/待验证] 结果也可能来自 Z` | 说明可验证该解释的实验 |
| 尚无足够信息 | `原文未报告/当前未读到……` | 避免将“未读到”写成“绝对没有” |

不要将猜测标为论文事实，也不要把无源的技术直觉包装成已发现的缺陷。

## 2. 六个有价值的审查问题

### 2.1 研究命题是否明确？
- 论文研究的问题在形式上是否被完整定义？
- 声称解决的问题与评价指标是否一致？
- 训练与推理场景是否与命题中的使用场景对应？

### 2.2 创新贡献是否可分离？
- 真正新提出的运算、目标、数据流程或理论性质是什么？
- 是否只是更大模型、更多数据或更强计算预算？
- 是否存在可替代的简单基线？
- 消融是否隔离了关键模块或与骨干网络的交互？

### 2.3 假设与适用边界如何？
- 方法是否隐含 i.i.d.、标注质量、模型容量、平稳性、可访问检索库等条件？
- 换一类样本、领域或资源预算时结论是否仍可能成立？
- 论文提供多少针对边界情况的直接证据？

### 2.4 结果能否归因？
- 对照条件、随机性与调参预算是否可比？
- 观察到的提升是否也可由数据、compute、训练时长、benchmark 选择解释？
- 是否披露失败案例、方差与无效果的实验？

### 2.5 方法能否复现？
- 是否给出足以理解实验结论的架构/算法细节、数据处理、训练和评估设置？
- 缺少超参数、随机种子、软件版本或资源预算时，是否影响复现难度？
- 不把“论文没有公开源代码”自动视为方法不正确。

### 2.6 成本和风险是否被考虑？
- 若声称 efficient，报告的是训练计算、推理延迟还是整体成本？
- 推理成本、数据标注、存储或外部依赖是否转移了成本？
- 对安全、偏差、隐私等敏感问题，是否给出适用的测试而非泛泛保证？

## 3. 结论审核规则

每一条批判性结论遵循：

`被审查的原文论断 → 论断所依赖的证据 → 证据不足或前提 → 更谨慎的解释 → 需要的验证`。

例如（纯示例）：

> `[解释性分析]` 论文声称改进 OOD 泛化，但主要结果来自同域测试（Table X）。这能支持同域性能提升，尚不足以单独支持 OOD 结论。后续可采用独立跨域数据集验证。

这里的 `Table X` 是格式占位符，执行真实任务时必须替换为已核实位置；不能照搬该示例作为真实批评。

## 4. 严格避免的写法

- 没有实验就写“实验证明模块有效”。
- 缺少消融就直接写“这个模块无效”。
- 论文未给时间复杂度就捏造 Big-O。
- 论文未报告特定数据集，就说“在该数据集表现差”。
- 只根据方法复杂、数学难，就说“缺乏可解释性”。
- 基于一条评估曲线断言论文“不可复现”。
- 为凑满三点局限而写没有事实依据的空泛批评。

## 5. 将批判转化为研究问题

生成开放问题时给出可操作形式：

1. **问题**：哪一处假设/归因/性能不足尚未解决？
2. **假设**：改变 X 是否会影响 Y？
3. **验证**：应采用什么对照、数据、指标或理论证明？
4. **价值**：若答案为真，会改变方法的哪一项结论？
5. **可行性/资源**：哪些信息论文已提供，哪些仍需获取？

不要把“可能更好”直接写成未来创新贡献。严谨的研究启发应可被反驳、可被验证。

## 6. 轻量批判输出模板

```markdown
### 审查项：[名称]
- **论文结论**：[原文事实 + 锚点]
- **已报告证据**：[实验/定理 + 锚点]
- **边界**：[解释性分析，具体缺口]
- **替代解释**：[推测/待验证，若适用]
- **验证建议**：[数据、控制变量、指标或证明]
```

优先输出 2–4 项真正改变论文结论理解的审查点，而非长篇低价值的限制清单。
