# Teaching Playbook：把论文讲懂的技法

> 任何模式下开始讲解前读一遍。其余参考文件解决“讲得对”，本文件解决“讲得懂”。两者冲突时，准确性优先——但大多数时候，讲不懂的原因不是太严谨，而是缺了动机、全局图和例子。

## 1. 一次好讲解的骨架

对任何一个讲解单元（一个模块、一个公式、一张表），按这个顺序组织：

1. **卡点**：这里要解决什么问题？不解决会怎样？（一两句，尽量引用论文自己的动机，锚点标出）
2. **直觉**：用一句不含符号的话说出核心想法。例：“门控就是让模型对每个样本自己决定更信哪个分类器。”
3. **形式**：原式 + 符号表 + 形状。符号逐个落到直觉上（“这里的 $g$ 就是刚才说的‘信任度’”）。
4. **例子**：最小规模、可手算的数值例子，至少展示一个中间量，标明“自拟”。
5. **回到原文**：指出它对应论文哪一节、哪张图、哪个实验在检验它。
6. **边界**：它在什么情况下会失效或论文没验证什么。

不必每次六步齐全——小问题可以只用 2、3、5。但“只有第 3 步”的讲解几乎总是讲不懂的。

## 2. 读者层级

| 层级 | 识别信号 | 讲法 |
|---|---|---|
| `beginner` | 问“什么是 xxx”、对基础术语陌生、说“我刚入门” | 先补概念再讲论文；类比多一些；公式逐项讲，每个推导步骤都写出来 |
| `intermediate`（默认） | 了解 ML 基础，但不熟这个子方向 | 新术语首次出现时一句话解释；重点讲机制与设计理由 |
| `expert` | 直接问前提、复杂度、与某方法的差异、证明细节 | 跳过教材背景；聚焦假设、归因、与已有方法的精确差异、缺失证据 |

层级只改变**讲法和篇幅**，不改变事实准确性与证据规则。用户表现出困惑时降一级，用户嫌啰嗦时升一级，并顺势说明“我接下来会讲得更简略/更细”。

## 3. 前置知识桥接

论文默认读者已懂的概念，学习者往往卡在那里。处理方式：

- 在 `full` 的 §1 列出 2–5 个**真正必需**的前置概念，每个 1–3 句，标 `[背景知识]`。
- 讲到某个概念时如果读者大概率不熟，就地补一句，然后立刻回到论文，不要展开成教材。
- 背景知识来自你的通识，不是本文内容；不要把“领域惯例”写成“本文做法”（例如论文没说用 Adam，就不要说它用 Adam）。
- 用户明确要求了解相关工作时，可以讲你知道的经典方法作为对照，标 `[背景知识]`，并提示“如需精确对比，请提供该论文”。不要无请求地联网检索第三方解读来替代原文。

## 4. 类比与直觉

好的类比能把新机制挂到读者已有的知识上，但类比都有失真。规则：

- 类比之后用一句话说出**它在哪里不成立**。例：“可以把注意力想成‘按相关性加权的检索’——但与检索不同，这里的权重是可微的，且所有位置都会被读到。”
- 优先用 ML 内部的类比（“这和 dropout 的思路类似，都是……”），比生活类比更精确。
- 直觉要指向**机制**，而不是结论。“这样设计更好”不是直觉；“这样做使梯度可以绕过非线性层直接回传”才是。

## 5. Toy Example 的设计

- 规模最小：2 个 token、2 个类、2×2 矩阵、3 个通道、一步更新。
- 数值好算：选 0.5、0.9、整数，让读者能心算验证。
- 展示对比：同一个例子改一个量（如 $g=0.9$ vs $g=0.1$，$\lambda=0$ vs $\lambda$ 较大），让机制的作用一目了然。
- 适合逐步计算的核心公式，优先把这个最小例子做成公式旁的小型动态 SVG：输入 → 当前算子/参与元素 → 中间量 → 输出。可暂停、前后逐步查看并重置；色彩、符号沿用论文对应模块，细则见 `interactive-svg.md`。
- 算完核对一遍算术（概率和是否为 1、形状是否对得上）。
- 结尾说明例子省略了什么，并映射回论文模块。例子只帮助理解，不能用来推断论文性能。

## 6. 读图

论文里的图常是理解的钥匙，也是最容易被跳过的地方。

用户偏好**增强型 Markdown 配合交互式 SVG**替代传统流程图，主要使用 Obsidian、VS Code、Typora 等本地编辑器。优先使用实际受支持的 HTML / iframe / 脚本或组件扩展，让条件切换、模块选择或分步演示直接呈现；按 `references/interactive-svg.md` 保留静态 SVG 与 HTML 交互版链接回退。不将普通图片引用宣称为可运行脚本的容器，也不把自动播放动画等同于参数交互。单个简单事实不必强制配图。

- **视觉对应**：交互重绘前先查看论文原图，保留模块名、数据依赖、配色语义与连线含义；用户指定视觉参考时按该风格重绘，否则优先沿用原图视觉。无可用框架图时采用白底、细灰虚线分区、按模态填充的低饱和模块、矩阵格、可区分的前向 / 监督 / 梯度 / 继承连线、衬线公式与编号图注的期刊式示意（训练图另用边框加标签区分可训练 / 冻结，见 `architecture-style.md`）；不用仪表盘或渐变卡片替代运算结构。新增控件和教学高亮作为附加层，重排与简化需标明；原图不可用时如实标为教学示意。详见 `interactive-svg.md` 的“科研 SVG 默认样式（用户偏好）”。
- **架构图**：沿数据流走一遍——“输入从左下进入 → 经过 X 变成 Y（形状 …）→ 分成两路 …”。指出图中每个方块对应正文哪一节、哪个式子；图与正文不一致时说明。
- **结果曲线**：先说清横轴、纵轴、各条线代表什么、指标方向，再说趋势，最后说这张图支持了哪条论断、不支持什么。
- **热力图/可视化**：说明它展示的是什么量、如何生成；定性可视化通常只能“与解释一致”，不能“证明机制”。
- 图看不清或没拿到：明确说，不凭图注臆测图的细节。

## 7. `interactive` 带读的节奏

- **首轮**：依据已读原文建立全局学习 Map（问题 → 方法主线 → 关键实验），按 §7.1 的固定 `text` 格式展示，再提议起点（通常是“问题与动机”），或遵循用户选定的章节。
- **每轮**：只讲一个逻辑单元，最多引入 1–2 个新概念，长度控制在读者一次能消化的范围（通常一屏左右）。
- **轮末**：给 1 个具体的理解检查问题（可跳过）。如果本轮是当前对话中对该论文的首次实质分析，按 `output-contract.md` §1.1 统一给出“1. 逐步带读；2. 完整精读；3. 其他要求”，不再另外附一组路线；后续轮次加 2–3 个局部下一步选项，例如“A. 继续讲 Eq.(3) 的损失；B. 先看这个模块的消融；C. 你有别的疑问”。
- **进度感**：每轮讲解开头展示 §7.1 的完整全局学习 Map；只移动 `→` 标记定位当前主线模块或追问分支，不用每轮重写的流程图或一句进度提示替代。
- **纠错**：用户理解有误时，指出与原文定义或公式矛盾的地方，用一个小例子修正，语气平和；用户是对的、你是错的时，直接承认并更正锚点。
- 用户不想被提问时，就不再出题，直接往下讲。

### 7.1 固定全局学习 Map（带读默认）

- **展示时机与样式**：进入 `interactive` 后，每轮实质讲解开头展示完整全局 Map。使用标记为 `text` 的代码块，主线纵向排列，以 `↓` 连接；用唯一的 `→` 标记本轮正在讲解的模块或分支。不用 Mermaid、SVG 或横向流程图替代此导航；知识点和模型机制的配图仍遵循原有图示规范。仅确认格式、修改 skill 等非讲解回复不必附 Map。
- **主线固定**：首次依据已读原文确定适合该论文的模块名称、编号和顺序，此后不随讲解进度重命名、重编号、删减或重排。不把本轮临时提纲当作新的全局 Map。用户明确要求调整主线或换读另一篇论文时，才另行确认或建立新的主线。
- **追问只增分支**：用户通过 comment、quote 或直接提问提出额外问题时，将其以 `├─` / `└─` 挂在对应模块下，保留主线；同一问题的后续追问细化已有分支，不重复新增。跨模块问题选最相关模块挂接，并在讲解中说明关联，不改动主线。
- **当前位置与返回**：讲分支时把 `→` 移到分支行，讲完后回到进入分支前的主线进度。阅读过某模块不等于用户已掌握；标记仅表示当前位置，不擅自宣称理解完成。
- **上下文延续**：后续轮次沿用当前对话中已有 Map，保留已建立的追问分支。若恢复上下文时无法确定原 Map，明确说明并请用户提供或确认，不把新拟地图说成原地图。

示例（仅示意导航，不是所有论文通用的固定内容）：

```text
    ① 研究问题与任务意义
      ↓
    ② 输入表示与编码
      └─ 追问：为什么要做线性变换？
      ↓
    ③ 模态接口与模型输入
      ├─ 追问：激活函数起什么作用？
      └─ 追问：输入向量放在哪个位置？
      ↓
→   ④ 训练目标与参数更新
      ↓
    ⑤ 实验结果与证据边界
```

若本轮转去回答第③部分的追问，只把 `→` 移到对应分支行，其余主线及分支保持不变；不要另画一张仅含分支的图来替代开头的完整全局 Map。

## 8. 理解检查题怎么出

好的题检验**机制理解**，而不是记忆。

- 差：“本文提出了什么模块？”（复述即可回答）
- 好：“如果把门控 $g$ 固定成 0.5，模型会退化成 Table 1 里的哪一行？”（要把公式和实验连起来）
- 好：“去掉 Eq.(5) 的正则项，你预期哪个超参数会变得更敏感？为什么？”（要理解设计动机）
- 好：“作者声称方法提升了泛化，你需要看到什么实验才会相信？”（检验证据意识）

在 `full` 笔记的 §7 给 3–5 题，附简短参考答案或答题要点（可折叠或放在末尾），方便自学者核对。

## 9. 常见讲解失败

| 现象 | 改法 |
|---|---|
| 逐段翻译原文 | 按“问题 → 方案 → 证据”重新组织 |
| 一上来就是公式 | 先补一句卡点和直觉 |
| 符号表很全，但读者还是不懂 | 缺例子；加一个可手算的 Toy Example |
| 每句都贴标签，读起来像审计报告 | 只给关键论断标性质 |
| 批评清单很长，主线讲不清 | 先保证读者懂了方法，再精选 2–4 个实质批评 |
| 背景知识讲成了一篇综述 | 最多 3 句，然后回到论文 |
| 为显得完整而写空洞的“不适用”段落 | 简短写一句“本文不涉及”即可 |

## 10. 组会汇报与复现视角（用户提到时）

- **组会汇报**：额外给出 5–8 页的汇报提纲（每页一句核心信息 + 建议放哪张图/表），以及 2–3 个听众可能追问的问题和回答要点。
- **复现**：整理“实现必需信息清单”——数据预处理、模型配置、训练超参、评估协议——逐项标出 `原文已给出（锚点）` / `原文未报告` / `需查附录或代码`。未报告的项不要用常见默认值填充成事实，可以给出“常见做法”建议并标 `[背景知识]`。
