# Deep Reading Workflow：九阶段论文精读流程

> 仅在执行全文系统精读或需要恢复阅读阶段时加载。本文件是执行手册；输出结构以 `output-contract.md` 为准。

## 0. 输入契约与适配

- 输入最少需要可读的 PDF、arXiv 正文页/PDF 或用户提供的正文。链接失效、扫描模糊、仅有标题时，明确当前可读取的内容；无法获得论文则请求上传 PDF，不能根据学科常识填充论文事实。
- 用户要求精读时为 `full + intermediate + 中文 Markdown`。只问某一式或图时切至 `focused`，只读必要的定义、上下文、附录证明与直接证据；只想了解大意时用 `quick`，可以只完成本流程的第 1–4 阶段。
- 论文 PDF 和 arXiv 是**研究对象的原始来源**，不是 Zotero/Drive 等外部知识库连接。不要无请求搜索第三方解读来替代原文。讲解前置概念时可使用你的通识，但标为 `[背景知识]`，不与本文内容混淆。
- 有多个论文版本时，基于用户提供或实际获得的版本分析；不要混合不同版本的数字、公式与结论。

## 1. 建立可核查 Paper Map

内部构建以下记录（没有信息使用 `unavailable`，不虚构）：

```yaml
paper:
  title: "..."
  authors: "..."
  venue_or_arxiv: "..."
  arxiv_id: "..."
  version: "..."
  source_type: pdf | arxiv_html | arxiv_pdf | text
  coverage: complete | partial | abstract-only
sections:
  problem: ["§1", "§2"]
  method: ["§3"]
  experiments: ["§4"]
  limitations: ["§5"]
figures: ["Fig.1", "Fig.2"]
equations: ["Eq.(1)", "Eq.(2)"]
tables: ["Table 1"]
missing: ["appendix PDF"]
```

该对象用于内部导航，不必原样展示。章节号、图表编号只取实际核实的值。检查 PDF 是否双栏、公式是否断裂、表格列是否错位、图注与图是否一致；能检查页面时优先用页面图像复核可疑位置。

## 2. 背景与研究动机：构建因果链

使用五问：
1. 当前任务是什么？输入、目标输出和评价目标是什么？
2. 现有方法（限文中介绍的）常见做法是什么？
3. 具体瓶颈或失败模式是什么？它在哪些条件下出现？
4. 作者提出了什么技术假设？为什么可能解决瓶颈？
5. 作者目标是提升准确性、效率、鲁棒性、可解释性，还是解决新任务？

对每个推论追溯至引言、问题定义或相关工作段落。将“作者声称现有工作存在问题”与“现有工作客观全部存在该问题”分开。

## 3. 问题形式化与学习目标

梳理 `输入 X → 目标 Y → 参数 θ → 优化/推断机制 → 评估指标`。

- 明确监督学习、生成学习、自监督学习、强化学习等任务属性。
- 写清数据分布、条件变量、预测空间、损失、约束和隐含独立性假设。
- 数学未完整形式化时，描述论文明确给出的元素；可补充教学形式化但标记 `[解释性分析]`。
- 找出假设与实验设置间的冲突或未核实项。

## 4. 贡献解构与技术总览

针对每条作者声明的贡献，使用“**已有方案 → 本文改变 → 试图解决的瓶颈 → 文中证据 → 边界**”。

绘制文本信息流：`原始输入 → 表征/预处理 → 主干/模块 → 目标/损失 → 训练更新 → 推理输出`。若模型同时有训练/推理路线，分别叙述。

关键原则：特征拼接、注意力机制或某项 loss 不自动构成创新；以作者与基线的实际差异判定。

## 5. 方法精读与算法走查

识别贡献最集中的 1–4 个方法单元，逐个应用 `method-and-formula.md`，讲法按 `teaching-playbook.md` §1 的“卡点 → 直觉 → 形式 → 例子 → 回到原文 → 边界”组织：

- 先用一段话说明整体机制，再分析模块。不要直接跳入公式符号。
- 主架构图沿数据流走一遍，把图中每个方块对应到正文小节与公式（`teaching-playbook.md` §6）。
- 对每个模块写：`功能 / 输入 shape / 变换 / 输出 shape / 与上下游依赖 / 训练和推理差异`。
- 对关键算法给出数据流与逐步流程。若提供简化伪代码，标明为“教学整理版”，避免伪装成论文原文。
- 选取少量对理解方法有决定性作用的公式逐层讲解；重复/简单公式可以概括。
- 如果存在等价公式、数学假设、维度对不上的疑问，先核查原文定义和附录；仍不明确则保留不确定性。

## 6. 数学理解与 Toy Example

优先识别：主目标函数、核心概率表达式、结构变换公式、梯度/优化更新、推理与采样公式。

每个核心式至少交代：原式、符号、做什么、为什么、与整体系统关系、证据锚点。复杂情形增加推导与示例；给出 Toy Example 时明确哪些数值/特征是自拟。

**不要**依靠 Toy Example 推出原论文性能结论。`小例子帮助直觉理解` 与 `证明算法实际有效` 是两种不同证据。

## 7. 实验问题和证据复盘

对每个主要实验先写“试图验证的命题”，再写数据、指标、基线、实验预算、结果、允许推断的结论。按照 `experiment-analysis.md` 检查：
- 主实验与 SOTA 对比是否公平；
- 消融是否真实检验各模块；
- 是否报告训练预算、模型规模、随机种子、统计方差；
- 下游任务、数据泄漏和测试集污染是否影响结论；
- 性能、资源成本与稳定性的权衡。

实验结果必须保留指标方向、单位及比较条件；禁止混用百分点变化和相对百分比。

## 8. 批判性分析与知识内化

- 根据 `critical-review.md` 将批评分成 `已被证实的限制`、`报告不足`、`合理研究假设`。
- 为难点给出至少一个有价值的理解途径：Toy Example、模块替代假设、边界条件、问答检验、训练/推理对照。
- 自检：能否回答“若删掉最重要的创新模块，哪个假设或计算关系会被破坏？论文有消融证据吗？”

## 9. 成品组织与覆盖说明

使用 `output-contract.md` 定义的章节顺序，记录：
- 阅读来源的身份与版本；
- `complete / partial / abstract-only` 及附录覆盖；
- 最关键的式、图、表的定位；
- 哪些重要结论是原文事实、解释或推测；
- 未能核实的内容。

输出长篇精读时优先保留：问题定义、创新机制、数学细节和实验可验证结论；压缩冗余背景，不缩减关键证据。超过单轮可合理承载的规模时，交付最大可信覆盖、标明遗漏，并按用户意图继续重点章节。

## 模式与中断处理

| 情况 | 决策 |
|---|---|
| 用户只给论文、没说要什么 | `quick`：给一页地图；首次分析完成后按 `output-contract.md` §1.1 提供“1. 逐步带读；2. 完整精读；3. 其他要求” |
| 用户只问一条公式 | `focused`：定位定义、前后公式和依赖，不生成全文报告 |
| 用户要做组会汇报或复现 | 在相应模式上追加 `teaching-playbook.md` §10 的汇报提纲或复现清单 |
| 用户要求“像导师一样带我读” | `interactive`：一轮只讲一个概念，询问具体困惑 |
| 只能获取摘要 | `abstract-only`：只分析摘要明确支持的信息，不能自称精读全文 |
| 论文附录/图表不可读 | 标记范围，限定影响，不自行补充不存在的实验 |
| 有版本冲突 | 明示版本并仅基于一个已核实版本做数值和公式对照 |
| 只有用户粘贴部分正文 | 标记 `partial` 和粘贴范围；不推断剩余章节 |
| 用户纠正符号或页码 | 回查来源，更新证据锚点并说明更正，不坚持先前错误 |
